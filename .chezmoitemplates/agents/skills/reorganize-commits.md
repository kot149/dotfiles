# reorganize-commits

Skill for reorganizing the commit history in the `<MB>..HEAD` range into **easy-to-review logical units**. It combines 3 kinds of operations:

- **Split**: when one commit changes too much or mixes several concerns, divide it into logical units
- **Combine**: when follow-ups on the same concern (typo fixes, review feedback, WIP) left the history fragmented, merge them into one
- **Reorder**: swap the order so the review reads naturally (prerequisite changes first)

Because this rewrites history destructively, **always save a dedicated recovery ref** before starting and **verify the final tree matches the saved tree** afterwards. Never change the code content itself.

## Prerequisites

- The working directory is inside a Git repository
- The `origin` remote is configured (so the base can be determined locally). `gh` is only a fallback for when the base call is ambiguous
- The current branch is not a protected branch (`main` / `master` / `develop`, etc.)
- No uncommitted changes (if there are any, agree on how to handle them with the user first)
- No rebase / merge / cherry-pick in progress

## Reorganization Criteria

### Things to split into standalone commits

The goal is to let the reviewer separate "diffs I can skip" from "diffs I must read". The following always get **their own commit**:

- **Pure code moves / renames**: file moves, extracting a function into another file, bulk symbol renames, anything with no behavior change. Judge by whether `git show -M -C --stat` detects a rename/copy, or whether the diff is "deleted lines identical to added lines"
- **Generated artifacts**: regenerated OpenAPI clients, protobuf/gRPC stubs, GraphQL type definitions, DB schema snapshots, lock files (`package-lock.json`, `uv.lock`, `Cargo.lock`), snapshot test updates. Judge by path or `DO NOT EDIT` / `generated by` headers. Keep the generator source (schema definitions, etc.) separate and order **source first, artifact second**
- **Formatting-only changes**: bulk formatter / linter runs, import sorting, indentation fixes
- **Dependency additions / updates**: manifest and lock file updates
- **Config / infra changes**: CI settings, build settings, anything whose concern differs from application code

### Things to combine

- Follow-up fixes to the same logical change (`fix typo`, review feedback, `lint fix`, `WIP`, `wip2`)
- Commits that only touch up just-added code (from the reviewer's view the diff just goes back and forth)
- An implementation commit and its test commit (when the tests should be read together with the implementation. Keep them separate when a TDD-style tests-first order is effective)

### Granularity guide

- One commit is one concern. If the message reads "Add A and B" with an `and`, it is a split candidate
- A hand-written change over a few hundred lines is a split candidate. Still, never split mechanically by line count
- Do not over-split either. Never slice down to units meaningless on their own (where the build breaks)
- Keep each commit building and testing cleanly where possible

## Steps

### 1. Check the state

Run the following in parallel:

- `git status --porcelain=v1 -b` — confirm no uncommitted changes and no rebase/merge in progress
- `git rev-parse --abbrev-ref HEAD` — current branch name
- `git log --oneline -30` — recent history
- `git rev-parse --symbolic-full-name @{u}` — check whether the branch has an upstream. If it fails, there is no upstream and all target commits are unpushed
- If upstream exists (after `<MB>` is determined in Step 2), compute `TOTAL=$(git rev-list --count <MB>..HEAD)` and `UNPUSHED=$(git rev-list --count <MB>..HEAD --not @{u})`, then `PUSHED=$((TOTAL - UNPUSHED))`. `PUSHED > 0` means the reorganization range contains already-pushed commits

If there are uncommitted changes, stop and present the following to the user in Japanese. **Never stash on your own.**

```
未コミットの変更があります。どう扱うか指示してください (コミットする / 変更を破棄する / 中止する)。
```

Stop on a protected branch, detached HEAD, or a rebase/merge in progress.

### 2. Determine the merge-target branch (base) and the start commit

Decide the base branch and fork point to fix the reorganization range. This is decidable from local information alone, so `gh` is not required.

{{ includeTemplate "agents/skills/_shared/git-base.md" . }}

If `git rev-list --count <MB>..HEAD` is 0, present the following to the user in Japanese and stop:

```
整理対象のコミットはありません (`<MB>..HEAD` にコミットがありません)。
```

**Never touch commits before `<MB>`.**

### 3. Survey the current state

```bash
git log --reverse --format='%h %s' <MB>..HEAD
git log --stat --format='%h %s' <MB>..HEAD
git diff <MB> HEAD --stat
```

When there are many commits or you need to see individual contents:

```bash
git show -M -C <SHA>
```

With `-M -C`, moves / renames render as renames, which tells you whether a move is pure.

List generated-artifact candidates (adjust patterns to the repository):

```bash
git diff <MB> HEAD --name-only
```

### 4. Draft the reorganization plan and get user approval

Following the "Reorganization Criteria" above, present the current-history to reorganized-history mapping to the user in Japanese. Present the following to the user in Japanese (fill in the actual SHAs, files, and counts):

```
現在の履歴 (5 コミット):
  a1b2c3d feat: ユーザーAPI追加 (32 files, +1840)
  e4f5g6h fix typo
  i7j8k9l レビュー指摘対応
  m0n1o2p wip
  q3r4s5t OpenAPI再生成

整理案 (4 コミット):
  [1] refactor: user ハンドラを handlers/ 配下へ移動   ← a1b2c3d のうち移動のみの差分
  [2] feat: ユーザーAPI追加                            ← a1b2c3d の残り + e4f5g6h + i7j8k9l + m0n1o2p
  [3] chore: OpenAPI スキーマ更新                      ← q3r4s5t のうち手書きのスキーマ定義
  [4] chore: OpenAPI クライアントを再生成              ← q3r4s5t のうち生成物

この方針で進めますか? 別の分け方を希望する場合は指示してください。
```

**Do not touch history until the user approves.** Present the approval request to the user in Japanese (e.g. `この方針で進めますか? 別の分け方を希望する場合は指示してください。`) and wait for an answer.

Handle pushed vs. unpushed history differently:

- If `PUSHED > 0`: the range rewrites already-pushed history. Get explicit confirmation with a selection prompt in Japanese (e.g. `push済みの<PUSHED>件を書き換えます。後でforce pushが必要になりますが進めますか? (進める / 中止する)`) and wait for an answer. Do not proceed on ambiguous replies.
- If `PUSHED == 0` or there is no upstream: unpushed-only range. A one-line notice in Japanese attached to the plan approval request is enough (e.g. `※ 未pushの履歴のみを整理します。`). No separate rewrite confirmation is needed.

At approval time, also decide which of the two execution methods to use:

- **Method A (full rebuild)**: rebuild the whole branch. Use this for wide ranges / many commits. No conflicts, but the original author dates are lost
- **Method B (partial rewrite)**: use interactive rebase to `edit` / `squash` / `fixup` / `reword` only the target commits. Use this when only part of the history needs reorganizing and the rest should keep its metadata

When unsure, use a selection prompt to have the user choose (present the choice to the user in Japanese, e.g. `方式A（全面組み直し）と方式B（部分書き換え）のどちらで進めますか?`).

### 5. Save a recovery ref (mandatory)

Before touching history, save HEAD outside `refs/heads` so it is retained without creating a branch:

```bash
BACKUP_REF="refs/backup/reorganize-commits/$(date +%Y%m%d-%H%M%S)/head"
ORIGINAL_SHA=$(git rev-parse HEAD)
git update-ref "$BACKUP_REF" "$ORIGINAL_SHA" ""
```

Check each command succeeds. The empty old-value argument requires a new ref: on collision, choose a fresh name, never overwrite an existing checkpoint. Confirm `git rev-parse "$BACKUP_REF"` equals `ORIGINAL_SHA` before proceeding.

Report the exact ref and SHA in Japanese: `復元用refを保存しました: <BACKUP_REF> (元の HEAD: <SHA>)`. Keep the ref until the user explicitly decides to remove it.

### 6-A. Method A: full rebuild

```bash
git reset --soft <MB>
git reset
```

`--soft` collapses the commits while keeping all changes, and the following mixed reset unstages them. Check `git status --short` that the expected changes are unfolded.

Then continue to Step 7.

### 6-B. Method B: interactive rebase

Point at the parent of the target range and rewrite the todo non-interactively via `GIT_SEQUENCE_EDITOR`.

Example turning a split target into `edit`:

```bash
GIT_SEQUENCE_EDITOR="sed -i.bak 's/^pick <SHORT_SHA>/edit <SHORT_SHA>/'" \
  git rebase -i <TARGET_SHA>^
```

Example turning follow-up commits into `fixup`:

```bash
GIT_SEQUENCE_EDITOR="sed -i.bak -e 's/^pick <SHA_B>/fixup <SHA_B>/' -e 's/^pick <SHA_C>/fixup <SHA_C>/'" \
  git rebase -i <SHA_A>^
```

- macOS `sed` cannot take an empty string for `-i`, so use `-i.bak`
- `<SHORT_SHA>` is the short SHA shown by `git log --oneline`
- When reordering is needed, swapping lines with `sed` is accident-prone. Prepare a script that writes the whole todo file in a scratchpad, or leave the interactive rebase to the user
- **When there are multiple split targets, process them one commit at a time.** Marking several as `edit` at once makes recovery hard

Once stopped at `edit`, return that commit's changes to the working tree:

```bash
git reset HEAD^
```

Then continue to Step 7. When Step 7 is done, run `git rebase --continue` to move on.

### 7. Re-stack commits in logical units

Following the plan agreed in Step 4, repeat per unit:

```bash
git add <FILES_FOR_UNIT...>
git commit -m "<commit message>"
```

- **Never use `git add -A` / `git add .`.** Always name files explicitly
- When splitting at hunk granularity inside a file, interactive `git add -p` is unavailable, so go through a patch:
  ```bash
  git diff -U3 <FILE> > <SCRATCH>/unit-N.patch
  # Edit <SCRATCH>/unit-N.patch to keep only the hunks for this unit
  git apply --cached --check <SCRATCH>/unit-N.patch
  git apply --cached <SCRATCH>/unit-N.patch
  ```
  Hunk headers (`@@ -a,b +c,d @@`) must match the line counts of the hunks kept. If hand-counting is tedious, have `git apply --cached --recount` recompute them. After applying, always check the staged content with `git diff --cached`; if it drifted, `git reset` and redo
- For a move-refactor commit, confirm `git show -M --stat` recognizes it as a rename afterwards. If not, the move and edits are mixed
- Match commit messages to the repository's existing style (`git log --oneline -20`). Follow the [[commit]] skill conventions and do not add `Co-Authored-By`
- After each commit, check the remainder with `git status --short`

Once all changes are committed, confirm `git status --short` is clean. **Never silently discard leftovers.** Present unexpected remainders to the user in Japanese (e.g. `想定外の残差があります: <status>。どう扱うか指示してください。`).

For Method B, `git rebase --continue` here. On conflicts with later commits, **do not `--abort`**; present the following to the user in Japanese and confirm the handling (resolve by hand / abort):

```
後続コミットとコンフリクトしました。`--abort` せずに中断しています。手動で解決しますか、それとも abort しますか?
```

### 8. Verify against the backup (mandatory)

Verify the reorganized HEAD tree **exactly matches** the saved recovery ref tree. This is the heart of this skill.

```bash
git diff "${BACKUP_REF}" HEAD
git diff "${BACKUP_REF}" HEAD --stat
```

- Empty output means OK (identical trees = the final product is unchanged by the reorganization)
- Any output means **NG**. The code content changed during reorganization

Double-check by comparing tree hashes:

```bash
BACKUP_TREE=$(git rev-parse "${BACKUP_REF}^{tree}")
HEAD_TREE=$(git rev-parse "HEAD^{tree}")
[ "${BACKUP_TREE}" = "${HEAD_TREE}" ] && echo "TREE_MATCH" || echo "TREE_MISMATCH"
```

- `TREE_MATCH` means success. Present the following to the user in Japanese:

  ```
  検証結果: ツリー一致 (TREE_MATCH)。最終内容は復元用ref <BACKUP_REF> と同一です。
  ```

- On `TREE_MISMATCH`, report it in Japanese and ask for the recovery plan. Never run `git reset --hard "${BACKUP_REF}"` without approval. Before an approved recovery, preserve any current uncommitted / untracked work and appropriately end any in-progress rebase / merge / cherry-pick; reset alone is not a safe way to abort an operation:

  ```
  検証結果: ツリー不一致 (TREE_MISMATCH) を検出しました。履歴の書き換え中に内容が変わっている可能性があります。
  復元用ref: <BACKUP_REF> (元の HEAD: <SHA>)
  復元方法の判断をお知らせください。こちらで勝手に復元は行いません。
  ```

This does not verify that each commit builds and tests cleanly. When needed, point the user to `git rebase --exec '<test command>' <MB>`.

### 9. Report the results

Present the following to the user in Japanese (fill in refs, SHAs, and verification result):

```
整理が完了しました。
- 復元用ref: <BACKUP_REF> (そのまま残しています。削除は後日の判断にお任せします)
- 整理前: `git log --oneline <MB>..<BACKUP_REF>` / 整理後: `git log --oneline <MB>..HEAD`
- 検証結果: <ツリー一致 (TREE_MATCH) / ツリー不一致 (TREE_MISMATCH。ステップ8の結果を記載)>
- force push が必要です。`git push --force-with-lease origin HEAD` はユーザー自身で実行してください (AI側では実行しません)。
- 戻す場合: 現在の作業内容を退避し、進行中の操作を適切に終了してから、承認のうえ `git reset --hard "<BACKUP_REF>"`
```

- The recovery ref (`${BACKUP_REF}`) and that it stays as-is (deletion is the user's later call)
- The before/after history comparison (`git log --oneline <MB>..${BACKUP_REF}` vs `git log --oneline <MB>..HEAD`)
- The tree-diff verification result (MATCH / MISMATCH)
- That a force push is needed, and that **the AI does not force push** (`git push --force-with-lease origin HEAD` is for the user to run)
- How to recover safely (step 8 prerequisites, then `git reset --hard "${BACKUP_REF}"`)

### 10. Recovery ref cleanup

Do not delete refs automatically. List saved checkpoints with:

```bash
git for-each-ref --format='%(refname) %(objectname:short)' refs/backup/reorganize-commits/
```

Once force push and behavior checks pass and the user explicitly chooses deletion, remove only the exact checkpoint ref:

```bash
git update-ref -d "${BACKUP_REF}"
```

## Notes

- **Never skip saving the recovery ref.** Never proceed to rewriting without Step 5
- **Never skip the tree-diff verification.** Never report completion without confirming `TREE_MATCH` in Step 8
- **Never run on a protected branch**
- **Never touch commits before `<MB>`**
- **Do not incorporate the base in this skill.** Always pin the start to the merge-base (`<MB>`) so nothing changes besides the history reorganization
- **Never `--abort` / `--skip` on conflicts on your own.** Ask the user to decide
- **Always verify staged content after a hunk-level split.** Patch-based splitting can sweep in the wrong hunk, so confirm with `git diff --cached` that only the intended hunks are staged before committing
- **Never use `git add -A` / `git add .`**
- **Never rewrite pushed history without explicit user confirmation.** When `PUSHED > 0`, get approval via a selection prompt. When unpushed-only, a one-line notice is enough
- **Never force push.** That is the user's job
- When the range contains merge commits, reorganizing linearizes the history. Warn the user beforehand and get approval
- When the branch only has accumulated `fixup!` / `squash!` commits, [[autosquash]] is safer and faster than this skill. To fold uncommitted changes into existing commits, use [[fixup]]
