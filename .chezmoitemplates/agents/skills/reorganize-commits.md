# reorganize-commits

`<MB>..HEAD` の範囲にあるコミット履歴を、**レビューしやすい論理単位**へ整理し直すスキル。次の 3 種類の操作を組み合わせる。

- **分割**: 1 コミットの変更が多すぎる / 複数の関心事が混ざっている場合、論理単位ごとに分ける
- **統合**: 同じ関心事に対する修正の繰り返し (typo 修正、レビュー指摘対応、WIP) で細切れになっている場合、1 つにまとめる
- **並べ替え**: レビューの読み順が自然になるよう順序を入れ替える (前提となる変更を先に置く)

破壊的な履歴書き換えを伴うため、**必ずバックアップブランチを作成**してから作業し、**整理後にバックアップと最終ツリーが一致することを検証**する。コードの中身は一切変えない。

## ユーザーへの選択提示

このドキュメントで「選択提示」と書いてある箇所は、選択肢を提示してユーザーに選ばせることを指す。選択UIツール (`AskUserQuestion` など) が使える agent ではそれを使い、無い agent では同じ選択肢を番号付きリストのプレーンテキストで提示し、番号または自由記述で答えてもらう。どちらの場合も回答を得るまで次の手順へ進まない。

## 前提

- 作業ディレクトリが Git リポジトリ配下であること
- `origin` リモートが設定されていること (base をローカルで特定するため)。`gh` は base の判断が割れた場合の補助にのみ使う
- 現在ブランチが保護ブランチ (`main` / `master` / `develop` など) でないこと
- 未コミット変更が無いこと (ある場合は事前にユーザーと処理方針を合意する)
- rebase / merge / cherry-pick が進行中でないこと

## 整理の判断基準

### 独立したコミットに切り出すもの

レビュアーが「中身を読まなくてよい差分」と「読むべき差分」を分離できるようにするのが目的。以下は**必ず単独コミットにする**。

- **純粋なコード移動 / リネーム**: ファイル移動、関数の別ファイルへの切り出し、シンボル名の一括変更など、振る舞いが変わらないもの。`git show -M -C --stat` で rename/copy として検出されるか、diff が「削除された行と追加された行が同一」かで判別する
- **自動生成物**: OpenAPI クライアントの再生成、protobuf/gRPC スタブ、GraphQL 型定義、DB スキーマのスナップショット、lock ファイル (`package-lock.json`, `uv.lock`, `Cargo.lock`)、スナップショットテストの更新。パスや `DO NOT EDIT` / `generated by` ヘッダで判別する。生成元の変更 (スキーマ定義など) とは分け、**生成元 → 生成物の順**に並べる
- **フォーマットのみの変更**: formatter / linter の一括適用、import 並べ替え、インデント修正
- **依存の追加・更新**: マニフェストと lock ファイルの更新
- **設定・インフラの変更**: CI 設定、ビルド設定など、アプリケーションコードと関心事が異なるもの

### まとめるもの

- 同一の論理変更に対する後追い修正 (`fix typo`, `レビュー指摘対応`, `lint 修正`, `WIP`, `wip2`)
- 追加したコードをその直後に手直ししているだけのコミット (レビュアーから見ると差分が往復するだけ)
- 実装コミットとそのテストコミット (テストが実装と一体で読まれるべき場合。テストだけを先に置く TDD 的な順序が有効な場合は分けたままでよい)

### 粒度の目安

- 1 コミットは 1 つの関心事。コミットメッセージが「A と B を追加」のように `and` / 「〜と〜」でつながるなら分割候補
- 手で書いた変更が数百行を超えるコミットは分割候補。ただし機械的に行数で割らない
- 逆に分割しすぎない。単独では意味を成さない (ビルドが通らない) 単位まで刻まない
- 各コミットは可能な限り単体でビルド・テストが通る状態にする

## 手順

### 1. 状態を確認する

以下を並列で実行:

- `git status --porcelain=v1 -b` — 未コミット変更と進行中の rebase/merge が無いことを確認
- `git rev-parse --abbrev-ref HEAD` — 現在ブランチ名
- `git log --oneline -30` — 直近の履歴

未コミット変更がある場合は中断してユーザーに確認する。**勝手に stash しない。**

保護ブランチ上、detached HEAD、rebase/merge 進行中の場合は中断する。

### 2. マージ先ブランチ (base) と起点コミットを確定する

整理範囲を確定するため base ブランチと分岐点を決める。ローカルの情報だけで決まるので `gh` は必須にしない。

{{ includeTemplate "agents/skills/_shared/git-base.md" . }}

`git rev-list --count "$MB"..HEAD` が 0 なら整理対象が無い旨を伝えて終了する。

**`<MB>` より前のコミットは絶対に触らない。**

### 3. 現状を調査する

```bash
git log --reverse --format='%h %s' <MB>..HEAD
git log --stat --format='%h %s' <MB>..HEAD
git diff "$MB" HEAD --stat
```

コミット数が多い場合や個別の中身を見る必要がある場合:

```bash
git show -M -C <SHA>
```

`-M -C` を付けることで、移動 / リネームがリネーム扱いで表示され、純粋な移動かどうかを判定できる。

生成物の候補を洗い出す (リポジトリの実態に合わせてパターンは調整する):

```bash
git diff "$MB" HEAD --name-only
```

### 4. 整理方針を立ててユーザー承認を得る

上記「整理の判断基準」に沿って、現在の履歴 → 整理後の履歴の対応を提示する。例:

```
現在の履歴 (5 コミット):
  a1b2c3d feat: ユーザーAPI追加 (32 files, +1840)
  e4f5g6h fix typo
  i7j8k9l レビュー指摘対応
  m0n1o2p wip
  q3r4s5t OpenAPI再生成

整理案 (4 コミット):
  [1] refactor: user ハンドラを handlers/ 配下へ移動   ← a1b2c3d のうち移動のみの差分
  [2] feat: ユーザーAPI追加                            ← a1b2c3d の残り + e4f5g6h + i7j8k9l + m0n1o2p
  [3] chore: OpenAPI スキーマ更新                      ← q3r4s5t のうち手書きのスキーマ定義
  [4] chore: OpenAPI クライアントを再生成              ← q3r4s5t のうち生成物

この方針で進めますか? 別の分け方を希望する場合は指示してください。
```

**ユーザー承認を得るまで履歴に触らない。** 承認時に、次のどちらの方式で実行するかも確定する。

- **方式 A (全面組み直し)**: ブランチ全体を作り直す。整理範囲が広い / コミット数が多い場合はこちら。コンフリクトが発生しない代わりに、元コミットの author 日付は失われる
- **方式 B (部分書き換え)**: interactive rebase で対象コミットだけ `edit` / `squash` / `fixup` / `reword` する。整理対象が一部だけで、他のコミットの情報を保ちたい場合はこちら

判断に迷う場合は選択提示でユーザーに選ばせる。

### 5. バックアップブランチを作成する (必須)

履歴に触る前に、**必ず**バックアップブランチを作成する。

```bash
CURRENT_BRANCH=$(git rev-parse --abbrev-ref HEAD)
TIMESTAMP=$(date +%Y%m%d-%H%M%S)
BACKUP_BRANCH="backup/${CURRENT_BRANCH}-reorg-${TIMESTAMP}"
git branch "${BACKUP_BRANCH}"
```

作成後、`git branch --list "${BACKUP_BRANCH}"` で存在確認をしてからでないと次に進まない。バックアップの HEAD SHA (`git rev-parse "${BACKUP_BRANCH}"`) をメモしておき、後の検証で使う。

バックアップブランチ名をユーザーに提示する。

### 6-A. 方式 A: 全面組み直し

```bash
git reset --soft "$MB"
git reset
```

`--soft` で全変更を保持したままコミットを畳み、続く mixed reset で unstage する。`git status --short` で想定の変更が展開されていることを確認する。

以降は Step 7 へ。

### 6-B. 方式 B: interactive rebase

対象範囲の 1 つ前を base に指定し、`GIT_SEQUENCE_EDITOR` で todo を非対話に書き換える。

分割対象を `edit` にする例:

```bash
GIT_SEQUENCE_EDITOR="sed -i.bak 's/^pick <SHORT_SHA>/edit <SHORT_SHA>/'" \
  git rebase -i <TARGET_SHA>^
```

統合したい後続コミットを `fixup` にする例:

```bash
GIT_SEQUENCE_EDITOR="sed -i.bak -e 's/^pick <SHA_B>/fixup <SHA_B>/' -e 's/^pick <SHA_C>/fixup <SHA_C>/'" \
  git rebase -i <SHA_A>^
```

- macOS の `sed` は `-i` に空文字を渡せないので `-i.bak` を使う
- `<SHORT_SHA>` は `git log --oneline` で表示される短縮 SHA
- 並べ替えが必要な場合、`sed` での行入れ替えは事故りやすい。todo ファイル全体を書き出すスクリプトを scratchpad に用意するか、ユーザーに対話式 rebase を委ねる
- **分割対象が複数ある場合は 1 コミットずつ順に処理する。** まとめて `edit` にすると事故のリカバリが難しい

`edit` で停止したら、そのコミットの変更をワーキングツリーへ戻す:

```bash
git reset HEAD^
```

以降は Step 7 へ。Step 7 が終わったら `git rebase --continue` で次へ進む。

### 7. 論理単位ごとに commit を積み直す

Step 4 で合意した方針に沿って、単位ごとに:

```bash
git add <FILES_FOR_UNIT...>
git commit -m "<コミットメッセージ>"
```

を繰り返す。

- **`git add -A` / `git add .` は使わない。** 常にファイルを明示指定する
- ファイル内の hunk 単位で分ける必要がある場合は、対話式 `git add -p` を **ユーザーに手動実行してもらう** よう案内する (AI が自動化しない)。パッチを scratchpad に書き出して `git apply --cached` する方法も取れるが、適用結果は必ず `git diff --cached` で確認する
- 移動リファクタのコミットは、移動後に `git show -M --stat` で rename として認識されることを確認する。認識されない場合は移動と編集が混ざっている
- コミットメッセージはリポジトリの既存スタイル (`git log --oneline -20`) に合わせる。[[commit-message]] スキルの規約に従い、`Co-Authored-By` は付けない
- 各コミット後に `git status --short` で残差を確認する

全ての変更をコミットし終えたら、`git status --short` がクリーンであることを確認する。**残った変更を勝手に握りつぶさない。** 想定外の残差があればユーザーに報告する。

方式 B の場合はここで `git rebase --continue`。後続コミットとコンフリクトが発生した場合は **`--abort` せず** ユーザーに報告し、対処方針 (手動解決 / abort) を確認する。

### 8. バックアップとの差分検証 (必須)

整理後の HEAD と、バックアップブランチのツリーが**完全に一致**することを検証する。これがこのスキルの本丸。

```bash
git diff "${BACKUP_BRANCH}" HEAD
git diff "${BACKUP_BRANCH}" HEAD --stat
```

- 出力が空であれば OK (ツリーが同一 = 整理前後で最終成果物が変わっていない)
- 出力に何か含まれていれば **NG**。整理中にコード内容が変わってしまっている

追加で tree ハッシュを比較して二重確認:

```bash
BACKUP_TREE=$(git rev-parse "${BACKUP_BRANCH}^{tree}")
HEAD_TREE=$(git rev-parse "HEAD^{tree}")
[ "${BACKUP_TREE}" = "${HEAD_TREE}" ] && echo "TREE_MATCH" || echo "TREE_MISMATCH"
```

- `TREE_MATCH` であれば成功
- `TREE_MISMATCH` の場合は **ユーザーに即報告し、リカバリ方針を確認する**。自己判断で `git reset --hard "${BACKUP_BRANCH}"` などの破壊的操作をしない (ユーザーが承認すれば実行してよい)

各コミットが単体でビルド・テストが通ることまでは検証しない。必要な場合は `git rebase --exec '<test command>' "$MB"` をユーザーに案内する。

### 9. 結果報告

以下をユーザーに伝える:

- バックアップブランチ名 (`${BACKUP_BRANCH}`) と、そのまま残す旨 (削除は後日ユーザー判断)
- 整理前後の履歴の対比 (`git log --oneline <MB>..${BACKUP_BRANCH}` と `git log --oneline <MB>..HEAD`)
- ツリー差分検証の結果 (MATCH / MISMATCH)
- force push が必要な旨、および **AI は force push しない** こと (`git push --force-with-lease origin HEAD` はユーザーが実行)
- リカバリ方法 (`git reset --hard "${BACKUP_BRANCH}"`)

### 10. バックアップブランチの後始末

削除は AI 側で自動的に行わない。ユーザーが force push 後、動作確認を経て問題がなければ手動削除する運用を案内する:

```bash
git branch -D "${BACKUP_BRANCH}"
```

## 注意事項

- **バックアップブランチ作成は省略しない。** Step 5 を飛ばして書き換えに進むことは絶対にしない
- **ツリー差分検証は省略しない。** Step 8 の `TREE_MATCH` を確認せずに完了報告しない
- **保護ブランチ上では実行しない**
- **`<MB>` より前のコミットは触らない**
- **base の取り込みはこのスキルでは行わない。** 起点は常に merge-base (`<MB>`) に固定し、履歴の整理以外の変化を起こさない
- **コンフリクト時に勝手に `--abort` / `--skip` しない。** ユーザー判断を仰ぐ
- **hunk 単位の複雑な分割は AI が自動化しない。** ユーザーに `git add -p` を委ねる
- **`git add -A` / `git add .` は使わない**
- **force push はしない。** ユーザーの責務
- 範囲内に merge コミットがある場合、整理すると履歴が線形化される。実行前にユーザーへ警告し、承認を得る
- 既に `fixup!` / `squash!` コミットが積まれているだけの状態なら、このスキルではなく [[autosquash]] のほうが安全で速い。未コミット変更を既存コミットへ寄せたいだけなら [[fixup]] を使う
